# Cut 5: implementation and QA plan

Status: proposed work plan, 29 October 2026. The existing code is a partial, unregistered prototype. It does not perform background classification, persist a budget or notify the desktop. Automatic model switching remains independently blocked by the [host boundary](evidence/v2-host-adapter-2.2.0.md).

## Intended behavior

In `auto` mode, discover public evidence and assess newly discovered models in the background without asking the user to assign models, select a classifier or reset a budget. **A model newly added after the first complete catalog baseline is the only normal trigger for classification inference.** Establish the initial baseline without model calls and try direct evidence; this may leave initial models with incomplete quality evidence. Use existing OpenCode authentication, not another account or billing integration. Prefer attributable, comparable evidence; distinguish a provisional estimate from a measured result. Keep all inference away from the coding prompt and do not change a session's selection. Turning the router off prevents new classification after the control has been accepted; a request already issued may still finish.

Use a conservative automatically renewing dispatch limit as a ceiling, not a target or a reason to schedule calls. The current prototype's four reservations per rolling 24 hours are unvalidated and must not be interpreted as a recommended daily frequency. The target is zero classification calls on ordinary days, and a single batched call when new models require inference where feasible. A reservation is not a provider-attempt, token, cost or subscription-allowance cap: OpenCode 2.2 can retry internally and returns text without usage. Notify users of dispatches and show these limitations accurately. Before release, measure cold start, new-model scenarios and retries to choose a limit.

## Current state and review findings

- The public-index adapter fetches a fixed OpenAI URL with size and time limits and matches exact paths. It has only narrow live coverage; it is not yet connected to the host catalog. Descriptive provider copy is not an independent benchmark.
- The worker accepts injected controls, cache, reservation, generation and notification functions. It is not registered in `src/index.ts`; these functions are test doubles. The caller, rather than the worker, currently promises that model IDs are public and that the classifier is calibrated. Neither promise is enforced by a production integration.
- `reserveDispatch` is a pure calculation, not durable accounting or an atomic reservation. The `4/day` default resets on restart if used without a store and does not bound actual provider attempts.
- A worker call that arrives while another call is in flight is currently coalesced with the first result; a materially different batch can be dropped. There is no durable pending queue, timer, retry or recovery loop.
- The prototype uses a changed fingerprint to decide whether a packet needs inference. That is too broad for the agreed new-model-only rule; the future scheduler must gate requests on durable first discovery, with fingerprints used for provenance rather than as an independent trigger.
- The worker's `notify` callback is only a test double. No GUI subscription, durable history, offline delivery or user-visible usage notice exists. It catches notifier errors without reporting delivery failure.
- The result shape is a provisional experiment. It omits task class, model version, comparator, explanation and freshness; a quote that exists in a source does not prove the assigned category. It is not suitable for routing or quality claims.
- Responses are checked for unload but not yet for catalog/evidence generation, changed connection, expired deadline or classifier revocation immediately before storing. A hung request can hold the in-flight worker indefinitely. An already-issued host operation may still consume allowance after the caller stops waiting.
- The isolated 2.2 loopback probe verifies text generation without session mutation. It does not establish real ChatGPT connection support, output cap, strict structured output, reliable cancellation or exact usage.

## Implementation sequence

### 1. Harden source, identity and assessment contracts

- Preserve and use the host's exact provider, host ID, provider model ID and any explicit canonical identity. Match only a public ID independently present in the official index; never upload a custom alias or local identifier. Record why an ID is unknown rather than guessing from its name.
- Pin the fixed URL and response type, disable redirects, bound bytes and time, and separate network, parse and unsupported-format errors. Retain source URL, retrieval time, content hash, model identity and the exact supporting public excerpt. Bound and sanitize untrusted text before prompting; treat instructions inside it as data.
- Represent provider descriptions, benchmark observations and classifier estimates as distinct evidence types. Do not infer measured performance, price, entitlement or quality from a source description or from a classifier's self-reported confidence. A versioned estimate includes its basis, uncertainty, task class, classifier/configuration, source references and expiry.
- Fix the validator and fingerprint to cover exact canonical identity, host-effective settings, evidence hash, extractor model/variant, calibration set and schema/prompt versions. Reject fabricated IDs, URLs and quotes, duplicate entries, invalid and partial outputs, oversized responses and incompatible benchmark configurations.
- Freeze an independent fixture set and a separate held-out set; include aliases, absent/retired models, changed source formats, duplicate IDs, contradictory claims, prompt injection and sources that do not support a comparison. Exact quotation matching is necessary, not sufficient semantic validation.

**QA:** credential-free unit tests plus a small, frozen, public source-coverage report. Document source access and terms; no blanket guarantee that every new model has an indexed public identity.

### 2. Durable state and rolling reservations

- Choose and verify a host-compatible local state mechanism shared by all plugin instances that can address the same account. The existing host `ctx.storage` exposes get/set, but its declarations do not provide compare-and-swap or transactions; do not assume those calls serialize a global budget. Verify Bun and OpenCode compatibility for the chosen locking/transaction mechanism before relying on it.
- Atomically reserve a dispatch **before** starting a model request, across simultaneous projects and process restarts. If exclusivity, storage integrity or clock ordering cannot be established, issue no request and retry automatically. Do not silently clear or overwrite corrupt state.
- Persist bounded rolling timestamps, source/assessment fingerprints, expiry, pending work, calibration results and bounded usage-notice history. Crash after reservation counts conservatively; don't refund an unknown request. Recover automatically after a rolling window, and protect against clock rollback and duplicate callbacks.
- Make reads and writes bounded and test temporary files/permissions, interrupted writes, corruption, clock changes, two concurrent instances, restart and disposal. Define retention and migration; do not store credentials, private paths, task prompts or arbitrary provider errors.

**QA:** integration tests with real storage primitives and separate processes, not only a shared in-memory mock. Demonstrate no more than the configured reservations under a race and safe automatic recovery after restart.

### 3. Rolling classifier calibration and replacement

- Build a deterministic bootstrap only when there is new-model work requiring inference: start with candidates that are host-available and exactly identified, favor documented suitability without assuming family names or price prove quality, and use previously verified calibration evidence where available. Record model ID, variant, evidence version and calibration version. Never let the candidate's judgment of itself count as independent validation. Compare combining a small calibration check with the first assessment against separate calls; choose only after testing correctness.
- Spend from the same rolling reservation budget for both calibration and assessments. A classifier disappearing or a calibration TTL expiring must not by itself initiate an inference call; discover and test a replacement only when a new model needs it. A restart, ordinary source refresh, changed catalog metadata or an unchanged model must not trigger reclassification. Persist successful identity assessments across restarts. Batch new models; ensure a stream of replacements cannot starve assessment work.
- If no candidate passes, broaden the candidates automatically within the limit and retry eligible known failures on the next window or relevant host change; do not duplicate an issued request with an unknown outcome. Reuse valid prior results where possible; clearly mark provisional estimates and their age. A provider outage or no eligible model cannot produce a successful call, but recovery requires no user action.
- Compare multiple candidates against held-out independent labels before picking thresholds. Measure factual grounding, invalid/refusal rates, provisional-estimate error, calibration stability, coverage and dispatches. Do not enable provisional rankings merely because JSON parses or a quote exists.

**QA:** fake provider tests first, followed by a small synthetic connected-account check with the user's requested low-frequency usage notice. Record actual supported behavior and available measurements; never collect private project data.

### 4. Scheduler, lifecycle and host transport

- Add one background owner that processes the durable queue of newly added identities. Coalesce a bounded discovery wave, try direct evidence, chunk only unresolved new-model work and retain arrivals while a call is active. Fingerprints track provenance and validity, never eligibility for inference. Changes arriving during a call must get a later run, not inherit or disappear into the first promise.
- Refresh the host catalog without model inference. Public evidence may refresh separately if needed, but a source TTL, source edit, model removal, catalog metadata change or expired assessment is not a reason to classify existing models again. Atomically establish a baseline only from a positively verified complete catalog; partial, failed and offline snapshots never initialize it. A model added before that baseline may be absorbed into it without inference; keep a durable set of previously discovered model identities and tombstones so removal and reappearance of a known ID are not mistaken for a new model. Queue newly added IDs once, even across restarts. Apply reliable catalog changes deterministically, and label outdated or incompatible evidence instead of silently spending usage. Retry failed work only for a still-pending new model, with deduplication, backoff and a strict cap; never blindly repeat an issued request with unknown outcome. A later recoverable connection or rolling-limit renewal may resume eligible pending new-model work, not schedule periodic reclassification. If an issued request has an unknown outcome and cannot be reconciled, retain its reservation and wait for a safe late result rather than automatically issuing a duplicate; this can leave that model unresolved. If a provider changes a model behind the same ID, this rule will not automatically reclassify it; document that trade-off.
- Integrate `ctx.experimental.generate.text` only after verified isolation and canonical identity mapping. Use bounded public inputs and bounded output processing. The host API does not expose a hard output-token cap or exact usage: do not advertise one. Preserve unknown outcomes on timeout or disconnect; do not issue a duplicate merely because a response is late.
- Recheck control generation, current catalog/evidence generation, classifier validity and lifecycle before issuing and before accepting results. Dispose timers and listeners; bound in-flight requests and memory. Test plugin ordering, recursion exclusion, removed models, changed account, stale results, disable before/after issuance, unload and late completion. If account/namespace continuity, state integrity or migration cannot be established, rebuild the baseline without inference and disclose that intervening discoveries may be lost.

**QA:** assert zero classifier dispatches on initial baseline, partial and offline startup, unchanged refreshes, restart, source/metadata changes, removal/reappearance, expiry, upgrades and classifier retirement. Test atomic discovery across processes, crash at each state transition, direct-evidence success, coalesced new IDs, arriving during a call, known failure versus unknown issued outcome, and late results. Then exercise the real packed plugin in a credential-free loopback fixture, including restart and concurrent project instances, followed by a bounded connected-account smoke test in a disposable session. No routing activation.

### 5. User-facing usage notification and inspection

- Publish a bounded server event after a dispatch begins, with a stable event ID, time, purpose (calibration or evidence assessment), plugin dispatch count and rolling limit. Never include evidence text, prompts, credentials, account IDs or raw errors.
- Deliver an OpenCode native toast when a connected desktop receives a new event; ensure multiple windows do not create duplicates. Persist a bounded pending notice alongside the reservation, then record a dispatch only when the invocation begins; preserve an explicit unknown status if a crash prevents confirmation. Users can inspect that history after the UI reconnects or opens later. If a notification cannot be delivered, do not retry the model call or claim it was delivered.
- Add a palette action for background usage and evidence status: recent dispatches, next eligible time, current classifier status and how many models are provisional. Explicitly show **tokens, cost and subscription allowance: unavailable** when not supplied by the host. Do not present reservations as actual provider attempts or include notices for skipped work.
- Update the user documentation with the default frequency, automatic budget renewal, disable behavior and what is and is not measured. User-facing notice wording must be tested for a genuine dispatch and for a reservation that is denied or cancelled before issuance.

**QA:** fake events, duplicate windows, disconnected desktop, reconnect, notification failure, truncated history and real desktop display. Confirm no inference from opening inspection.

### 6. Evidence and provisional-ranking evaluation

- Verify public identity, provenance, coverage and source changes against the held-out set; measure unsupported claims, wrong mappings, stale estimates and recovery. Estimates must retain their weaker provenance rather than becoming factual benchmark scores.
- Exercise profiles with independently labeled decision fixtures, including high-impact, ambiguous and long-context cases. Compare actual routed tasks against the frozen paired coding corpus only after the cut 3 host boundary is proven. Include classification dispatches and retries in total overhead; do not claim subscription savings without a reliable measurement.
- Before release, require observed beneficial routing and quality/latency gates from the PRD; false or weak provisional rankings are a failure to investigate, not an excuse to silently claim success.

**QA:** present source coverage, classifier selection/replacement, example notices, measured dispatch count and failures, changed/removed model cases and known gaps for user review. Do not enable production routing while cut 3 is unresolved.

## Immediate next step

Start with section 1 and replace the worker's fingerprint trigger with the discovery lifecycle; repair dropped-concurrent-batch and stale-result behavior before wiring anything to a real account. Then prove the shared durable reservation mechanism. Until both and the notification path pass, the existing code remains unregistered and no background model calls occur.
