# Cut 5: implementation and QA plan

Status: implementation and QA plan. The existing code is a partial, unregistered prototype. The experimental store persists reservations in tests, but the installed plugin does not classify, persist a production budget or notify the desktop. Automatic model switching remains independently blocked by the [host boundary](evidence/v2-host-adapter-2.2.0.md).

## Intended behavior

Cut 5 is distributed and runs as part of the plugin: no separate daemon, external classifier service, database server, system SQLite executable, API key, or additional installation is required. It uses OpenCode's existing model connection and may retrieve public evidence over HTTPS. Its durable SQLite data lives in a user-scoped local state directory outside the installed package so upgrades can preserve it; that data is owned and managed by the plugin. A runtime without the required built-in SQLite support must leave classification inactive and report the limitation, never silently depend on a separately installed tool.

In `auto` mode, discover public evidence and assess newly discovered models in the background without asking the user to assign models, select a classifier or reset a budget. **A model first observed after the saved baseline is the only normal trigger for classification inference.** Global release-time proof is not required; an older model omitted from both initial snapshots may be classified once when first observed. Establish the initial baseline without model calls and try direct evidence; this may leave initial models with incomplete quality evidence. Use existing OpenCode authentication, not another account or billing integration. Prefer attributable, comparable evidence; distinguish a provisional estimate from a measured result. Keep all inference away from the coding prompt and do not change a session's selection. Turning the router off prevents new classification after the control has been accepted; a request already issued may still finish.

Use a conservative automatically renewing dispatch limit as a ceiling, not a target or a reason to schedule calls. The current prototype's four reservations per rolling 24 hours are unvalidated and must not be interpreted as a recommended daily frequency. The target is zero classification calls on ordinary days, and a single batched call when new models require inference where feasible. A reservation is not a provider-attempt, token, cost or subscription-allowance cap: OpenCode 2.2 can retry internally and returns text without usage. Notify users of dispatches and show these limitations accurately. Before release, measure cold start, new-model scenarios and retries to choose a limit.

## Current state and review findings

- The public-index adapter fetches a fixed OpenAI URL with size and time limits and matches exact paths. It has only narrow live coverage; a local matcher now uses the host's explicit provider-facing model ID rather than its alias, and an unregistered resolver shares and caches bounded index fetches with failure backoff. They are connected to the scheduler in an unregistered fake-provider integration fixture, but not validated against the connected account. Descriptive provider copy is not an independent benchmark.
- Automatic extraction calibration is implemented in the integration pipeline: candidate selection, co-batched fixture validation, persistent pass/rejection cache, shared accounting and retirement/replacement are tested. The actual OpenCode transport passes a loopback test, but two live QA dispatches produced no assessment; the diagnostic reported an explicit invalid_request rejection. See [calibration verification](evidence/v2-automatic-calibration-2.2.0.md). Live compatibility and independent ranking-quality evaluation remain open.
- The worker accepts injected controls, cache, reservation, generation and notification functions. It is not registered in `src/index.ts`; these functions are test doubles. The caller, rather than the worker, currently promises that model IDs are public and that the classifier is calibrated. Neither promise is enforced by a production integration.
- A new, unregistered SQLite prototype atomically persists discovery and reservations. A Node multi-process test enforces a shared limit, and an isolated OpenCode 2.2 fixture exercises the store. A user-scoped path helper now checks private directory, database and sidecar permissions in local tests; it is not yet wired or proven against path-replacement races. The store persists bounded notices, assessment provenance and calibration checks transactionally. Recovery ownership, migration/failure coverage and production host concurrency verification remain before integration. `reserveDispatch` alone remains a pure calculation; the unvalidated `4/day` default does not bound actual provider attempts.
- The prototype serializes distinct worker batches with a bounded in-memory queue and rechecks controls before saving. A hung call can still block the queue; there is no durable pending queue, timer, retry or recovery loop.
- A dependency-injected scheduler prototype connects the discovery state machine to the experimental store and issues only pending new-model work. It is joined to the public resolver in an unregistered integration fixture, but not connected to the older worker or registered with the host; source mapping, transactional assessment provenance, extraction calibration and a pending-only retry driver have local coverage. Desktop notice delivery, live classifier compatibility, production connection freshness, crash ownership, restart continuation and host registration remain open. Lookup scans now have a per-run cap and a rotating in-memory cursor; the host integration must resume deferred work with backoff and handle restarts. The prototype now bounds individual waits and continues batches; timing out does not cancel a host request. The prototype worker still uses changed fingerprints when called directly and cannot be registered without the discovery gate.
- The worker's `notify` callback is only a test double. A read-only native evidence/history command and server RPC now exist; automatic toast delivery, GUI subscriptions and offline notice delivery remain unfinished. It catches notifier errors without reporting delivery failure.
- The result shape is a provisional experiment. It omits task class, model version, comparator, explanation and freshness; a quote that exists in a source does not prove the assigned category. It is not suitable for routing or quality claims.
- The integration pipeline rechecks catalog and control generations before accepting successful results; the scheduler bounds waits. Production connection identity, evidence changes and classifier revocation still need acceptance coverage. The older worker only rechecks controls and unload before saving. A hung request can hold the in-flight worker indefinitely. An already-issued host operation may still consume allowance after the caller stops waiting.
- The isolated 2.2 loopback probe verifies text generation without session mutation. It does not establish real ChatGPT connection support, output cap, strict structured output, reliable cancellation or exact usage.

## Remaining delivery checkpoints

Each checkpoint is reviewable independently. Keep the prototype unregistered until checkpoint 5 has passed; passing unit tests for a component does not activate it. All components ship inside the plugin. The local database is operational data, not a separate service.

1. **Make state and accounting production-capable.** Choose a user-scoped shared path independent of the project, establish private file/directory permissions and safe creation, and verify the `node:sqlite` runtime capability on every supported host. Version the schema and define atomic migrations, corruption detection and recovery; do not silently reset seen identities or reservations. Store pending work, bounded assessment/provenance records, calibrations and notice history in transactions. Design ownership so a second process cannot reinterpret an in-flight request as abandoned. Atomically reserve the shared rolling allowance and claim a batch, and atomically persist validated results with their completion state. An ambiguous crash or response must remain unknown; known unissued work may return to pending. The prototype now binds a claimed batch to a durable token, but callers can still assert that no dispatch occurred; enforce outcome preconditions and design owner-liveness recovery before integration. Define clock rollback, retries and disk-full behavior. **Exit:** separate-process race, crash-at-each-transition, migration, permissions, corruption, clock and restart tests pass in Node and the packaged OpenCode host; document OS/runtime limits.
2. **Connect evidence and identity.** Obtain current host inventory only when complete, preserve exact host/provider identity in memory, map to a public canonical ID without sending private aliases, and use bounded public source lookups. Collect direct comparable evidence where available before considering inference. Model source claims, assessments and their provenance separately; document uncertainty and do not turn provider descriptions or an extractor's confidence into measured quality. Freeze development and held-out identity/grounding fixtures before tuning. **Exit:** frozen tests cover alias collisions, missing public models, duplicate/conflicting entries, source errors, stale documents, prompt injection and unsupported comparisons. Produce a source-coverage report; unknown coverage is not success.
3. **Build a replaceable classifier and its evaluation.** Select deterministically from eligible host models using verified identity and available evidence. On pending new-model work only, reuse a previously validated classifier or calibrate a replacement against independently labeled examples. Compare a combined calibration-and-assessment call with separate calls; use the least costly option that passes the held-out checks. Bound input, output handling, candidate attempts and rolling dispatches; do not assume the existing four-per-day prototype is the final setting. Record classifier, prompt/schema and evidence versions. Evaluate grounding, false promotions/demotions, abstention, coverage and dispatch count. **Exit:** classifier replacement and retirement tests pass, no timer causes inference, and a frozen held-out report shows whether outputs justify use in later routing. If calibration or coverage fails, continue improving the path; do not label it complete or manufacture a rank.
4. **Complete scheduling and generation.** Join catalog events, durable discovery, source lookup, the calibrated classifier and the native stateless host transport. Process only pending new-model identities; bound/coalesce batches and continue remaining work without starvation, including when the first 16 items are temporarily unavailable. Remove the worker's independent fingerprint trigger. Revalidate the current catalog, connection, control generation and owner before dispatch and before committing results. Handle disable, unload, removal, host restart, deadlines and late results; a timeout must not hold the scheduler forever or automatically trigger a duplicate request. Retry eligible known failures with bounded backoff and renewal; never create periodic classification of known models. Clear timers and subscriptions on disposal. **Exit:** deterministic fake-provider and packaged-host tests demonstrate zero calls for baseline, refresh, restart, metadata/source changes, removal/reappearance, expiry and classifier retirement; actual new-model work is batched and neither lost nor duplicated under races and faults.
5. **Deliver notices and inspectable status.** Persist a bounded notice record with each reservation, distinguish reserved, issued and uncertain outcomes, and emit a stable-ID event for an actual dispatch. Connect desktop notifications and an inspection action through the native GUI/RPC interfaces; handle reconnects, offline windows, duplicate windows, delivery failure and cleanup. Show purpose, plugin dispatch count and renewal time; explicitly display unavailable token, cost and allowance measurements. Do not send a notice for a known unissued request and do not retry inference when notification delivery fails. **Exit:** automated GUI/RPC tests and a real desktop review show a readable notice and history, no duplicate event across windows, and zero inference when inspecting status. Decide and test the precise semantics for disconnected windows; do not claim delivery that cannot be observed.
6. **Prove the integrated cut before activation.** Run the packed plugin against the pinned 2.2 host with a loopback provider and synthetic models, testing restarts, multiple plugin instances, new-model arrival, failure, notice and no-session-mutation. Then run a bounded synthetic test on the already connected OpenCode account, with a visible usage notice and no private task content; record what the host actually exposes. Evaluate held-out evidence results and report first-run/new-model dispatches, errors and unknown usage, not estimated subscription savings. **Exit:** publish reproducible results and remaining limitations, pass build/typecheck/tests/docs/audit and review the user experience. Only then register automatic background classification. If connected inference, notification delivery or evidence quality cannot be demonstrated, keep the specific capability inactive and document the failure rather than claiming cut 5 complete.

### Review findings that must be resolved

- The prototype scheduler now skips unavailable identities, continues additional bounded batches and times out individual lookups/dispatches. Each run now examines at most 32 pending identities with per-lookup deadlines and retains an in-memory rotation cursor. An unregistered driver now coalesces wakeups and schedules pending-only work with backoff; host event wiring, restart-safe continuation and bounded runtime behavior still need verification. Its queue can reject an observation when full; a production observer must reconcile from a fresh complete catalog instead of losing that update. Timeout or disposal stops waiting but does not cancel an issued host request.
- The prototype now stores a validated batch and marks it complete in one claimed transaction, and rechecks controls before saving. The prototype also checks catalog/connection freshness before discovery, dispatch and persistence. A catalog adapter now ties those checks to the real CatalogStore revision, freshness and event monitoring, but it requires an explicit independently verified host completeness guarantee and is not registered. Direct-evidence atomicity, source identity, semantic grounding and durable provenance remain unfinished; the test callback is not a production classifier.
- The store has durable per-batch claim tokens but no process-liveness recovery, production notice delivery, full assessment provenance, secure path, or complete migration/recovery policy. The prototype now records bounded reserved/started/unknown/completed/cancelled notices with stable claim IDs, but has no desktop subscriber, crash-owner reconciliation or delivery guarantees. The store now persists the first shared dispatch limit and rejects mismatched callers; changing it safely, including migration and configuration, remains unfinished. A reservation remains charged even if a later control check prevents dispatch; define a safe explicit cancellation that cannot refund an issued or ambiguous operation.
- The store now persists bounded dispatch-status records, but the notification callback is still a test double and does not establish desktop delivery. The integration fixture now separates preflight from issuance and tests that a preflight failure creates no reservation or notice. Its notice callback distinguishes a confirmed start from a synchronous unknown outcome; actual desktop delivery is still unverified. The worker's separate cache/fingerprint path and the scheduler are not yet a single guarded production pipeline.
- Catalog `complete` is derived from response shape, not independently proven exhaustive host semantics. The [pinned-host source investigation](evidence/v2-catalog-readiness-2.2.0.md) found that startup can use a bundled or cached model snapshot followed by a background refresh, so newly observed identities need not be newly published. Verify refresh/readiness behavior and account/namespace continuity before treating the inventory as the baseline. An unregistered integration fixture now records verified public-source identities at baseline and suppresses classification when the host later exposes a matching pre-existing public model, including aliases. This reduces startup-refresh false positives; it does not establish completeness for missing, undocumented, or newly indexed older models. The user accepted first-observed semantics: global release-time proof is no longer a baseline activation requirement. Validate current host snapshot integrity and freshness before activation. State loss may miss models added during the gap; disclose it instead of creating a wave of false new-model calls.

**Dependency boundary:** Cut 5 can be implemented and tested independently of automatic session switching. The separate [host admission boundary](evidence/v2-host-adapter-2.2.0.md) remains a prerequisite for enabling routing; the final paired coding evaluation belongs to the integrated release, not a prerequisite for testing an isolated evidence lookup.

## Implementation sequence

### 1. Harden source, identity and assessment contracts

- Preserve and use the host's exact provider, host ID, provider model ID and any explicit canonical identity. Match only a public ID independently present in the official index; never upload a custom alias or local identifier. Record why an ID is unknown rather than guessing from its name.
- Pin the fixed URL and response type, disable redirects, bound bytes and time, and separate network, parse and unsupported-format errors. Retain source URL, retrieval time, content hash, model identity and the exact supporting public excerpt. Bound and sanitize untrusted text before prompting; treat instructions inside it as data.
- Represent provider descriptions, benchmark observations and classifier estimates as distinct evidence types. Do not infer measured performance, price, entitlement or quality from a source description or from a classifier's self-reported confidence. A versioned estimate includes its basis, uncertainty, task class, classifier/configuration, source references and expiry.
- Fix the validator and fingerprint to cover exact canonical identity, host-effective settings, evidence hash, extractor model/variant, calibration set and schema/prompt versions. Reject fabricated IDs, URLs and quotes, duplicate entries, invalid and partial outputs, oversized responses and incompatible benchmark configurations.
- Freeze an independent fixture set and a separate held-out set; include aliases, absent/retired models, changed source formats, duplicate IDs, contradictory claims, prompt injection and sources that do not support a comparison. Exact quotation matching is necessary, not sufficient semantic validation.

**QA:** credential-free unit tests plus a small, frozen, public source-coverage report. Document source access and terms; no blanket guarantee that every new model has an indexed public identity.

### 2. Durable state and rolling reservations

- Choose and verify a host-compatible local state mechanism shared by all plugin instances that can address the same account. The existing host `ctx.storage` exposes get/set, but its declarations do not provide compare-and-swap or transactions; do not assume those calls serialize a global budget. Verify Bun and OpenCode compatibility for the chosen locking/transaction mechanism before relying on it.
- Atomically reserve a dispatch **before** starting a model request, across simultaneous projects and process restarts. If exclusivity, storage integrity or clock ordering cannot be established, issue no request and retry automatically. Do not silently clear or overwrite corrupt state.
- Persist bounded rolling timestamps, source/assessment fingerprints, expiry, pending work, calibration results and bounded usage-notice history. Crash after reservation counts conservatively; don't refund an unknown request. Recover automatically after a rolling window, and protect against clock rollback and duplicate callbacks.
- Make reads and writes bounded and test temporary files/permissions, interrupted writes, corruption, clock changes, two concurrent instances, restart and disposal. Define retention and migration; do not store credentials, private paths, task prompts or arbitrary provider errors.

**QA:** integration tests with real storage primitives and separate processes, not only a shared in-memory mock. Demonstrate no more than the configured reservations under a race and safe automatic recovery after restart.

### 3. Rolling classifier calibration and replacement

- Build a deterministic bootstrap only when there is new-model work requiring inference: start with candidates that are host-available and exactly identified, favor documented suitability without assuming family names or price prove quality, and use previously verified calibration evidence where available. Record model ID, variant, evidence version and calibration version. Never let the candidate's judgment of itself count as independent validation. Compare combining a small calibration check with the first assessment against separate calls; choose only after testing correctness.
- Spend from the same rolling reservation budget for both calibration and assessments. A classifier disappearing or a calibration TTL expiring must not by itself initiate an inference call; discover and test a replacement only when a new model needs it. A restart, ordinary source refresh, changed catalog metadata or an unchanged model must not trigger reclassification. Persist successful identity assessments across restarts. Batch new models; ensure a stream of replacements cannot starve assessment work.
- If no candidate passes, broaden the candidates automatically within the limit and retry eligible known failures on the next window or relevant host change; do not duplicate an issued request with an unknown outcome. Reuse valid prior results where possible; clearly mark provisional estimates and their age. A provider outage or no eligible model cannot produce a successful call, but recovery requires no user action.
- Compare multiple candidates against held-out independent labels before picking thresholds. Measure factual grounding, invalid/refusal rates, provisional-estimate error, calibration stability, coverage and dispatches. Do not enable provisional rankings merely because JSON parses or a quote exists.

**QA:** fake provider tests first, followed by a small synthetic connected-account check with the user's requested low-frequency usage notice. Record actual supported behavior and available measurements; never collect private project data.

### 4. Scheduler, lifecycle and host transport

- Add one background owner that processes the durable queue of newly added identities. Coalesce a bounded discovery wave, try direct evidence, chunk only unresolved new-model work and retain arrivals while a call is active. Fingerprints track provenance and validity, never eligibility for inference. Changes arriving during a call must get a later run, not inherit or disappear into the first promise.
- Refresh the host catalog without model inference. Public evidence may refresh separately if needed, but a source TTL, source edit, model removal, catalog metadata change or expired assessment is not a reason to classify existing models again. Atomically establish a baseline only from a positively verified complete catalog; partial, failed and offline snapshots never initialize it. A model added before that baseline may be absorbed into it without inference; keep a durable set of previously discovered model identities and tombstones so removal and reappearance of a known ID are not mistaken for a new model. Queue newly added IDs once, even across restarts. Apply reliable catalog changes deterministically, and label outdated or incompatible evidence instead of silently spending usage. Retry failed work only for a still-pending new model, with deduplication, backoff and a strict cap; never blindly repeat an issued request with unknown outcome. A later recoverable connection or rolling-limit renewal may resume eligible pending new-model work, not schedule periodic reclassification. If an issued request has an unknown outcome and cannot be reconciled, retain its reservation and wait for a safe late result rather than automatically issuing a duplicate; this can leave that model unresolved. If a provider changes a model behind the same ID, this rule will not automatically reclassify it; document that trade-off.
- Integrate `ctx.experimental.generate.text` only after verified isolation and canonical identity mapping. Use bounded public inputs and bounded output processing. The host API does not expose a hard output-token cap or exact usage: do not advertise one. Preserve unknown outcomes on timeout or disconnect; do not issue a duplicate merely because a response is late.
- Recheck control generation, current catalog/evidence generation, classifier validity and lifecycle before issuing and before accepting results. Dispose timers and listeners; bound in-flight requests and memory. Test plugin ordering, recursion exclusion, removed models, changed account, stale results, disable before/after issuance, unload and late completion. If account/namespace continuity, state integrity or migration cannot be established, rebuild the baseline without inference and disclose that intervening discoveries may be lost.

**QA:** assert zero classifier dispatches on initial baseline, partial and offline startup, unchanged refreshes, restart, source/metadata changes, removal/reappearance, expiry, upgrades and classifier retirement. Test atomic discovery across processes, crash at each state transition, direct-evidence success, coalesced new IDs, arriving during a call, known failure versus unknown issued outcome, and late results. Then exercise the real packed plugin in a credential-free loopback fixture, including restart and concurrent project instances, followed by a bounded connected-account smoke test in a disposable session. No routing activation.

### 5. User-facing usage notification and inspection

- Publish a bounded server event after a dispatch begins, with a stable event ID, time, purpose (calibration or evidence assessment), plugin dispatch count and rolling limit. Never include evidence text, prompts, credentials, account IDs or raw errors.
- Deliver an OpenCode native toast when a connected desktop receives a new event; ensure multiple windows do not create duplicates. Persist a bounded pending notice alongside the reservation, then record a dispatch only when the invocation begins; preserve an explicit unknown status if a crash prevents confirmation. Users can inspect that history after the UI reconnects or opens later. If a notification cannot be delivered, do not retry the model call or claim it was delivered.
- Add a palette action for background usage and evidence status: recent dispatches, next eligible time, current classifier status and how many models are provisional. Explicitly show **tokens, cost and subscription allowance: unavailable** when not supplied by the host. Do not present reservations as actual provider attempts or include notices for skipped work.
- Update the user documentation with the default frequency, automatic budget renewal, disable behavior and what is and is not measured. User-facing notice wording must be tested for a genuine dispatch and for a reservation that is denied or cancelled before issuance.

**QA:** fake events, duplicate windows, disconnected desktop, reconnect, notification failure, truncated history and real desktop display. Confirm no inference from opening inspection.

### 6. Evidence and provisional-ranking evaluation

- Verify public identity, provenance, coverage and source changes against the held-out set; measure unsupported claims, wrong mappings, stale estimates and recovery. Estimates must retain their weaker provenance rather than becoming factual benchmark scores.
- Exercise profiles with independently labeled decision fixtures, including high-impact, ambiguous and long-context cases. Compare actual routed tasks against the frozen paired coding corpus only after the cut 3 host boundary is proven. Include classification dispatches and retries in total overhead; do not claim subscription savings without a reliable measurement.
- Before release, require observed beneficial routing and quality/latency gates from the PRD; false or weak provisional rankings are a failure to investigate, not an excuse to silently claim success.

**QA:** present source coverage, classifier selection/replacement, example notices, measured dispatch count and failures, changed/removed model cases and known gaps for user review. Do not enable production routing while cut 3 is unresolved.

## Immediate next step

Harden and connect the discovery lifecycle and transactional store, establish recovery ownership, and gate the worker on pending new-model work. Complete source, stale-catalog, timeout, classifier and notification gates before wiring anything to a real account. Until both and the notification path pass, the existing code remains unregistered and no background model calls occur.
