# Verification and release specification

**Scope:** PRD sections 7–8. This document specifies evidence required for v0.1, not evidence already obtained. Ordinary CI is credential-free. The tagged release workflow has not yet been verified end to end.

## First host spike

The maintainer evaluates OpenCode 1.19.4 CLI with matching plugin types in an isolated installation. Record exact host and plugin builds, operating system, setup, commands, scripted-provider observations, limitations, and pass/fail for [host capabilities](host.md), including [eligibility proof](catalog.md#contract). A scripted provider may simulate a host-identified OpenAI provider but does not prove real OpenAI access. The spike must demonstrate safe original-turn model and variant changes, override/pin semantics, discoverable controls, context evidence, session isolation, guard validation covering user actions, selection, turn, catalog and connection, the deadline, and no late mutation or duplicate request. A lost acknowledgement or commit error after possible application is indeterminate; it is never credited as a successful keep and blocks automatic release for that combination.

The maintainer records a go/no-go in a checked-in compatibility report. If a required capability cannot be demonstrated, that combination is unsupported for automatic routing. Investigate another explicitly pinned host or ship only an honestly labeled recommendation preview; do not claim v0.1 automatic routing succeeded. Desktop, TUI and v2 require separate evidence. Do not alter the user's global OpenCode setup for the spike.

## Test layers

| Layer | Required checks |
| --- | --- |
| Pure unit/fixture | Catalog unknowns, role evidence, profile decisions, context fit, variant compatibility, cooldown, explicit choice precedence and deterministic outputs. |
| Adapter contract | One original turn, actual selected model and variant observed by a scripted provider, no-op fallback, isolation, stale catalog and control guards, unavailable candidates, deadline, late completion, acknowledgement loss, controls and errors. Include one model-changing and one separate variant-changing scenario; always-keep fails. |
| Host integration | Load packaged plugin in each claimed host/surface; exercise actual control and dispatch paths. Verify UI state where relevant. A mock cannot establish a host's behavior. |
| Persistence/privacy | Consent off/on, allowlist, missing measurements, purge-on-access, byte bounds and deletion, corruption, permissions where supported, concurrent and late writes; pin state stays separate. |
| Packaging | Clean install, typecheck, build, test, dependency audit, archive contents, install/remove and rollback. Verify tagged-release automation end to end before release. |

All required tests must pass for each claimed combination. An unsupported host, ambiguous user selection, unknown account eligibility, or missing safe commit semantics must not silently become an automatic success.

## Performance gate

On a recorded reference machine and scripted host, run at least 100 warmed paired trials with plugin enabled and disabled using representative fixtures. Measure local policy time and added wall-clock time from plugin turn entry to actual dispatch, including discovery, validation, durable attempt recording, commit and fallback. Publish median and p95: local p95 must be under 50 ms and added dispatch p95 under 250 ms. Measure cold, slow, unavailable and stale-catalog paths separately. Force responses after the 200 ms decision deadline and assert no router mutation, preservation of the latest authoritative host selection, no late mutation, and no duplicate request; include an intervening user change. If the time bound or safe cancellation/commit guarantee cannot be met, automatic release is blocked.

## Quality gate

Freeze exactly 30 independent synthetic coding tasks before evaluation, with automated pass/fail checks, at least five each for straightforward changes, multi-file implementation, debugging, and long-context or ambiguity; pre-mark safety-critical tasks and checks. Predeclare infrastructure failure and rerun rules. Record environment, role mappings, models/variants, tools, timeouts, retry limits and execution order; use equivalent isolated workspaces and alternating or seeded randomized order.

For each task run one fixed preselected model/variant baseline with routing off and the Economy, Balanced and Quality profiles under equivalent limits; use the recorded alternating or seeded randomized execution order rather than requiring the baseline first. Publish all per-task paired outcomes, actual switches, missing data, exclusions and all attempts. For each profile, no safety-critical baseline pass may become a routed failure, and at most one non-critical baseline pass may fail when routed; gains on other tasks do not offset regressions. Each profile must actually change at least one model or variant. Missing access or any missing valid pair is incomplete, not pass. If a candidate fails, a fixed candidate reruns the entire frozen suite under the predeclared procedure. The maintainer records the decision and acknowledges the limited sample and model variability.

This gate requires a separately authorized live test account or budget using synthetic public fixtures; it is not run by ordinary CI and must not expose private conversation data or credentials. If unavailable, the gate is incomplete and only a preview can ship. No conclusion about ChatGPT subscription savings follows from the benchmark.

## Evidence binding and release checklist

The release owner confirms all mandatory test layers and host capabilities, documents supported versions/surfaces and installation/rollback, audits dependencies, publishes performance and paired quality results, and verifies release automation with a suitable non-production exercise before tagging. The package version must not be used as evidence of implemented behavior. An automatic v0.1 release requires every applicable PRD gate; otherwise label the artifact as a preview and state its limits.

For each release candidate, build from one exact immutable commit and create a separate immutable evidence manifest **after** the build, avoiding a self-referential commit hash. The manifest records the repository identity and full candidate commit SHA, package name/version, SHA-256 of the exact package archive to be released, lockfile digest, supported host builds/surfaces and compatibility-report digest, policy and fixture-corpus revisions/digests, CI run IDs and conclusions, performance and paired-evaluation artifact digests/results, and release-workflow dry-run evidence. Hash the completed manifest; then record maintainer approval in a **separate attestation** that identifies the candidate SHA, manifest digest, approver and approval time. The manifest must not contain its own digest or the attestation that refers to it. Link to artifacts that contain only synthetic or appropriately sanitized data; never include credentials or private conversation content. Missing, stale, revoked or failed evidence blocks the release.

The tag must point to that exact candidate commit, and the archive attached to the release must have the manifest's SHA-256. Rebuilding after approval, changing a tag, changing evidence or producing a different package digest invalidates approval and requires fresh evidence and approval. The release workflow must verify the tag's resolved commit, package digest, evidence manifest digest, separate approval attestation and the recorded successful gates before creating or updating a release; ancestry on `main` and a matching version alone are insufficient. Store the manifest and attestation in protected, immutable release-evidence artifacts associated with the exact candidate and attach both to the release. Define authentication and provenance for that store before implementation; do not assume an ordinary editable file or untrusted workflow input proves approval. The existing tag workflow does not yet enforce this contract and cannot by itself establish release readiness.

### Recommended GitHub implementation

Use GitHub Actions on this public repository with a dedicated protected `v0.1-release` environment, required reviewer, and administrator bypass disabled. A solo-maintainer repository may allow self-review; that proves an explicit approval occurred, not independent review. Require the approved release workflow to run from protected `main`, use full-SHA-pinned third-party actions, and prohibit pull-request or arbitrary-ref workflows from acquiring release write permissions. Restrict repository administration and environment editing to trusted maintainers. Protection configuration itself must be reviewed and recorded in the release evidence; an administrator who can change the rules remains in the trust boundary.

1. A candidate job checks out the exact protected-main commit, verifies CI and the compatibility/quality evidence for that SHA, builds the archive **once**, calculates SHA-256 of the archive and evidence inputs, and writes the manifest with the run ID, candidate SHA, and digest. It uploads archive, manifest and sanitized supporting evidence as run-scoped Actions artifacts, recording artifact IDs and digests. Do not treat artifact names as identities: GitHub artifacts can expire or be deleted, and a replacement has a different ID. Fail closed if any artifact is unavailable. GitHub's [artifact documentation](https://github.com/actions/upload-artifact) describes immutability and deletion behavior.
2. The same workflow run exposes the candidate SHA, archive digest, manifest digest, run ID and evidence links in its summary **before** the environment-gated publish job waits for approval. The reviewer checks those exact values and gate results. The approval is GitHub's environment review for that run/job; capture its reviewer, time and decision from GitHub's authenticated deployment review record as a separate approval attestation referring to the pre-approval manifest digest. [GitHub environment documentation](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments) describes reviewer and bypass controls. Configure the environment explicitly before production; referencing a nonexistent, unprotected environment is not acceptable.
3. After approval, the publish job retrieves artifacts by recorded run and artifact ID, verifies the manifest and archive SHA-256, approved run and reviewer record, required CI/evaluation gate results, protected-main candidate and tag-to-commit binding. It publishes **the same archive bytes**, without rebuilding. A new candidate, rerun that changes any artifact, moved tag, missing review or expired artifact requires a new candidate run and approval. PR-provided manifests, artifact names and user-controlled workflow inputs are not trusted evidence by themselves.
4. Generate GitHub [artifact attestations](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations) for the archive and manifest using the minimum necessary OIDC and attestation permissions, and verify them before publication with repository, expected signer-workflow and source-digest constraints. Provenance identifies the builder and source; it does **not** prove that tests passed or that an approval was meaningful. Attach the archive, manifest, separate approval evidence and attestation bundles to the release, and document independent verification. Do not claim Actions artifact retention is permanent or that a repository administrator cannot delete artifacts or change protections.

This is the selected design, not an implemented or tested pipeline. The existing `.github/workflows/release.yml` neither checks this evidence nor requires environment approval, so its release job is disabled. It must be replaced and validated with a non-production run before a v0.1 tag is created. Do not enable a production release environment or publish a release as part of the design work.

Acceptance: exercise a passing candidate and reject an older or moved tag, mismatched package/lockfile/fixture digest, missing or failed CI, absent approval, changed evidence, and artifacts built from a different commit. The non-production exercise must not create a public v0.1 release or require publication credentials for ordinary CI.
