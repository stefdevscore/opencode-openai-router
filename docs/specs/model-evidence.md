# Model evidence and background classification

Status: cut 5 in progress. A bounded public-index adapter, assessment validation, rolling dispatch-budget primitive and an isolated dependency-injected worker exist but are not wired into the installed plugin. Persistence, automatic classifier selection/calibration, desktop usage notifications, connected-account transport and ranking quality remain unfinished. No automatic classification or routing runs yet. The worker's dispatch-count message is exercised with a fake notifier only; it does not notify desktop users.

## Responsibility

On OpenAI models newly added after a complete initial catalog baseline, automatically collect public evidence and, if necessary, use a replaceable background classifier to produce a cached capability assessment or clearly labeled provisional estimate. Establish the initial baseline without model calls; use direct evidence where possible and label incomplete quality information. Users do not need to assign roles or choose an anchor. Coding-task assessment remains local; the background classifier does not run for each prompt. The host catalog alone authorizes selectable models and variants, not external scores or classifier output.

## Evidence and inference

Use host metadata for canonical identity, tools, modalities, limits and variants. Retrieve attributable public model documentation and coding evaluations where available. Provider guidance, independent benchmarks, measured local outcomes and model-generated interpretation must be distinguishable. Prefer documented structured sources; a bounded adapter or classifier may extract information from retrieved prose, but extracted claims require source references and validation. Evidence contents are untrusted data, never executable instructions.

A low-frequency inference call is part of the intended automatic experience. Prefer an isolated background generation through the existing OpenCode connection if the pinned host supports it without affecting coding conversations or session selection. This path consumes normal allowance. A separate paid API or keyed data source is optional future integration, not a v0.1 requirement; it must use an explicitly configured, host-managed connection and budget, never repurpose ChatGPT credentials as API credentials. No new billing path is selected silently. Provider choice and source coverage remain implementation deliverables, not proven capabilities.

Classification is automatic by default in auto mode, with disclosed, conservatively bounded dispatches and an automatically renewing limit; no opt-in, manual reset or model assignment is required. Users may disable the router or change limits. OpenCode 2.2 does not expose a per-call token cap or usage through its stateless text API; an invocation limit is not a guaranteed token, currency, provider-attempt or subscription-allowance limit. Exact enforcement requires a separately proven host capability. Neither background inference nor evidence lookup blocks a coding turn. During outages or a spent rolling limit, reuse available assessments and automatically resume eligible pending work when conditions recover. An issued request with an unknown outcome follows the conservative recovery rule below; never claim inference succeeded without a validated result.

## Trigger, cache and output

Fingerprint canonical model identity/version, routing-relevant catalog settings, evidence content hashes, classifier identity and prompt/schema version for provenance and cache validity. A changed fingerprint alone is **not** an inference trigger: classify only for a newly discovered model requiring it, including bounded retries of unresolved new-model work. Persist seen identities across restart and batch multiple new models within input/output limits. Catalog refresh, model removal, changed metadata, changed source text, schema changes and TTL expiry must not trigger classification of existing models. Apply safe source/catalog changes deterministically and mark stale or invalid evidence; do not misrepresent it as current. Deduplicate in-flight work, bound retries and negative-cache unavailable evidence. Exact batch, retry and reservation limits must be measured and specified in implementation.

Return a strictly validated structure containing exact candidate identity, task-class suitability, supported evidence references, comparative strengths/limitations, uncertainty, classifier/prompt version and retrieval times. Rank only host-listed candidates. Distinguish verified source claims from provisional estimates and do not present invented sources, prices or benchmark results as facts. Estimates must record their basis and uncertainty and be evaluated against held-out evidence before influencing routing. Self-reported confidence is not a calibrated success probability, and schema validity does not prove factual correctness.

Bootstrap a rolling classifier from host-available candidates using a versioned set of independently reviewed calibration examples, only when new-model work needs inference. If the current classifier disappears or fails, select and test a replacement when that pending work needs it; do not spend inference merely because the classifier changes or a timer expires. Choose candidates deterministically using known evidence, broaden the search when necessary, and bound attempts per rolling window. Record the classifier and calibration separately from the routed model. A candidate's estimate about itself is provisional, not independent validation. Never recursively trigger classification from classifier calls. If no model can be reached or validated, recover pending new-model work automatically without user intervention and retain prior valid data; do not claim availability, evidence or metering that does not exist. No implementation can guarantee successful calls during an outage.

Cache bounded validated assessments with provenance and fingerprints. Evidence expiry, removal or conflict invalidates the affected rank; it must not erase the last known record's provenance. Only future admissions use refreshed evidence. Lookup and classification cannot change an active conversation or apply a delayed routing decision. Use timeouts, bounded downloads, backoff and last-valid cache behavior; offline operation retains the host selection when no adequate candidate evidence exists.

## Discovery lifecycle

1. **Baseline:** The first successfully completed, authoritative OpenAI catalog snapshot establishes the durable set of seen identities atomically. An empty, partial, failed or offline response cannot establish a baseline unless the host positively proves it is complete, including when it is genuinely empty. Existing models use direct evidence; no baseline classification or calibration runs. A model added while no complete baseline is available may be included in the eventual baseline and will not generate a new-model event.
2. **Discover:** Compare later complete snapshots with the durable seen set. A previously unseen exact provider/model identity is recorded and queued atomically; repeated snapshots and restarts cannot lose or duplicate the event. Incomplete snapshots do not establish absence or newness. Retain seen identities and tombstones across removals, temporary disconnects, source changes and normal upgrades. Never evict a seen identity silently and then treat it as new; storage limits, corruption or unrecoverable migration require a safely rebuilt baseline without inference, with loss of intervening discoveries disclosed.
3. **Resolve:** Coalesce a short, bounded wave of pending identities, check their current eligibility, map to verified public identities and try direct evidence first. Models resolved without inference finish with no model dispatch. Work arriving during a dispatch remains queued for a subsequent batch. A model removed before dispatch is deferred; reappearance resumes its existing work rather than creating another event. Catalog availability does not prove account entitlement.
4. **Dispatch:** Only unresolved, eligible new-model work may initiate assessment or on-demand classifier calibration. Reuse a suitable verified classifier; try a deterministic candidate and replacement only when needed. Reserve shared usage atomically before dispatch, enforce the measured limit, and notify on actual plugin dispatch, including calibration. Batch where feasible without indefinite waiting. Host retries may make more than one provider attempt and are not separately visible.
5. **Finish or recover:** Validate identity, grounding, lifecycle and current catalog before storing results. Retry known failures of pending work automatically with bounded attempts per rolling window and backoff; the quota is a ceiling, not a timer for new inference. A timed-out or interrupted issued request is an **unknown outcome**, not proof of failure. Keep its reservation and accept a valid late result when safe; do not automatically send a duplicate solely because of timeout. If the host cannot reconcile the outcome, that work can remain unresolved without manual action. Surface its status truthfully and use available evidence. This deliberately favors low usage over guaranteed immediate assessment, since both cannot be guaranteed with this transport.
6. **Maintain:** Catalog and public-source refreshes, model removal/reappearance, cache expiry, changed metadata, schema changes, classifier retirement and elapsed time do not create new classification work. Mark invalidated evidence stale and preserve provenance. A model changed behind the same ID does not qualify as a newly added model. Account or provider namespace changes and state migrations must not turn an existing population into false new-model events; rebaseline without inference if continuity cannot be established.

A complete catalog and durable, concurrency-safe state are release prerequisites, not assumed capabilities. Until verified, keep classification unregistered. Deleting all operational state creates a new baseline; it cannot reconstruct events that occurred while history was absent. No classifier calls occur while disabled, though already-dispatched requests may finish and incur usage.

## Identity, ranking and privacy

Require exact provider/model/version correspondence, including reasoning configuration when it changes evaluation meaning. Use documented canonical identity or a source-provided explicit mapping; display-name or fuzzy matching is insufficient. Avoid sending custom aliases or arbitrary host identifiers externally: resolve to a verified public model identity first, otherwise leave it unverified.

Compare measured scores only when benchmark version, settings and agent/tool conditions are compatible. Separately label provisional estimates and their weaker basis; never represent them as measured scores. Produce task-class/profile rankings with traceable reasons, not a universal best-model score. Economy balances capability and efficiency; Quality favors capability; Balanced balances both. API prices and token counts do not measure ChatGPT allowance savings. Evaluate the risk of weak-evidence downshifts, particularly for uncertain/high-impact tasks, before enabling them in production.

No coding prompts, source, paths, private conversation, account identifiers, credentials or raw errors enter lookup/classification requests or caches. The cache stores only required public canonical identity, bounded assessment and provenance; it is operational state separate from optional observations. Automatic classifier calibration uses bounded public or synthetic extraction examples. A broader synthetic coding-quality evaluation is separate: it runs a frozen suite only with a disclosed allowance budget and user authorization, and must not touch private projects.

## Acceptance

- Prove at least one source adapter with exact identity, documented format/terms, attribution and tested coverage. Prove isolated native classifier invocation or document why it is unavailable. Do not claim universal zero-configuration coverage if new models lack usable evidence.
- Test add/change/remove, aliases, malformed and conflicting evidence, benchmark mismatch, malicious text, fabricated citations, unknown or unsupported variants, refusals, invalid/partial output and insufficient evidence. Verify evidence before it can authorize a switch.
- Assert zero inference on initial baseline, partial/offline startup, repeated refresh, restart, source or metadata change, model removal and reappearance, expiry, schema upgrade, classifier retirement and time passing. Test atomic baseline and discovery across concurrent processes, crash/restart at each transition, state loss and migration, bounded coalescing, direct-evidence success, concurrent new arrivals, negative cache, known failures, unknown issued outcomes, disable/unload, budget exhaustion and duplicate callbacks. Reserve usage before dispatch, reconcile actual usage when exposed, and report unknown rather than claim exact spending when metering is incomplete. The configured budget must state its enforceable unit; a currency cap requires trustworthy rates and reservation accounting.
- Freeze a held-out set of model evidence packets and independently reviewed expected claim/identity constraints before tuning. Measure grounded-claim errors, unsupported promotions/demotions, identity accuracy, abstention, coverage, cache effectiveness and usage. Include newly introduced models and equivalent names at different settings. Never validate rankings only by asking the same classifier to agree with itself.
- Evaluate actual automatic model/effort switches against the frozen coding corpus and report end-to-end regressions. Classification quality, local task-assessment quality and coding outcomes are separate tests. No result alone establishes savings or the globally best model.
