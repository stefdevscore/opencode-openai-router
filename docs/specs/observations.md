# Local observations specification

**Scope:** PRD FR-6. Observations are optional evaluation data, separate from the minimum control state needed for pins and cooldown. They do not determine task success or train the router in v0.1.

## Consent and schema

Collection defaults off. Enabling it is explicit and local; disabling it stops new writes and does not silently delete existing data. The user can inspect and delete records without a model call. No upload, remote telemetry, silent migration or classification service is permitted.

Use an explicit versioned allowlist. A record may contain only: schema version, timestamp, optional local pseudonymous session correlation, selected provider/model/variant, profile, kept/proposed/applied outcome, bounded reason codes, host-reported input/output token counts, elapsed durations, and coarse error/retry or independently verified task-outcome signals. Optional values are unknown or omitted when absent; zero must represent an actual zero. Versioned enumerations must be used for error/outcome codes: do not copy arbitrary host error messages or free text. Never include prompt, source, file path, credentials, raw tool output, request body, or raw conversation content.

Correlation is generated locally, scoped to the local store, never derived directly from a host session ID, and is not shared across installations. Provider/model/variant identifiers can be user-configured free text and may contain sensitive content: do not store raw identifiers in the observation log. If model-level grouping is needed, use locally generated random opaque aliases with no reversible identifier mapping persisted in this store; otherwise omit the field. Any identifier-to-alias lookup is in-memory only and may reset at restart, so aliases cannot be assumed stable across restarts. The plugin may display current host identifiers in its native inspection view, subject to the host's display rules, but must not copy them into the observation log. Bound and validate every field; never serialize arbitrary host strings or free-form error text. A response or error-free dispatch alone is not labeled successful task completion. Task outcomes may be recorded only when a documented verifiable signal is provided; otherwise leave unknown. Cache hits, subscription allowance and cost are not inferred from token counts.

## Storage and lifecycle

Before shipping, document and implement the exact platform-specific local path, file schema, directory/file permissions where supported, configuration, inspect/delete controls, and retention. Retention is **purged on access while collection is enabled**, not guaranteed deletion at age 30 days: on enabled startup and before every enabled write or inspection, evict records older than 30 days, then oldest records until the store has at most 10,000 records and at most 10 MiB, including framing/index data. After adding a record, enforce both limits again before acknowledging the write. No scheduler is required; if the plugin remains idle, is not running, or collection is disabled, older records can remain on disk until collection is enabled and the next purge occurs or the user explicitly deletes them. While disabled, inspection is read-only and filters expired entries from the view without updating the file; an explicit user-requested delete is the only allowed mutation of existing observations. This does not authorize creating a store while disabled. Each encoded record is at most 1 KiB; fixed enumerations are at most 64 ASCII bytes per code and opaque aliases at most 64 ASCII bytes. Reject oversized or malformed fields/records instead of truncating arbitrary untrusted text into the store. A shorter user-selected retention may be supported. Bounds are local, not a promise that previously exported copies can be removed. Never write to a repository by default.

Use bounded storage operations that cannot block or change a user turn if the store is corrupt, full, unavailable, unwritable, or deletion fails. Report a coarse local diagnostic when the host supports inspection. Coordinate writes, consent changes and deletion so no queued or late write recreates a deleted store after deletion completes or persists an observation after disabling completes. If the platform cannot enforce a proposed permission or atomicity guarantee, document the limitation and test fail-safe behavior before release. Session-control persistence is not an observation log and must be independently minimized and deletable.

## Acceptance

- Off: no observation file created or automatically updated, including startup purge, inspection, or queued writes after disabling; an explicit user deletion is permitted and must not recreate the store.
- On: only allowlisted fields appear; host failures, arbitrary strings, unknown token counts, and unverified outcomes cannot inject private data or false zeroes.
- Exercise purge on enabled startup, before and after write and on enabled inspection; disabled startup and read-only inspection; idle behavior; age/count/byte/record/field bounds; malformed and secret-bearing identifiers; explicit deletion; disabling; corrupt/unwritable storage; concurrent writes; and restart. Assert no raw identifier is persisted and no rejected oversized record is partially written. Deletion prevents queued writes from recreating old records; failures do not interrupt requests.
- Local measurement does not establish subscription allowance savings. Document what is measured and what remains unknown.
