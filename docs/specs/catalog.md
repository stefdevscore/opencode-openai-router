# Catalog and eligibility specification

**Scope:** PRD FR-2. Catalog normalization translates only facts supplied by the verified OpenCode host into a connection-scoped snapshot. It does not rank model quality, authenticate users, probe credentials, or maintain a fixed list of OpenAI model IDs.

## Contract

A snapshot identifies its host connection and revision/freshness proof and whether its inventory is complete for the relevant connection and provider. Each candidate contains the exact host provider/model IDs, eligibility status and source, effective context limit if known, relevant input/output and tool capabilities if exposed, and enabled variant identities and semantics if known. Preserve `unknown` versus explicit `unsupported`; retain provenance so inference is distinguishable from a host fact. An empty complete eligible list is different from an incomplete, failed or unavailable discovery operation. Absence from an incomplete list is unknown, never proof a model was removed or is ineligible.

Only a host-identified OpenAI provider associated with the active connection is in scope. A model listed by a catalog is not automatically accessible to the current account. Provider identity, connection, eligibility, host disablement, and retirement must be established by verified signals. Unknown access is ineligible for a switch. Generic compatible endpoints and OpenAI-branded models under other providers are out of scope.

Eligibility proof must be a documented host guarantee for the **active connection** that the candidate is enabled and selectable under that connection, with an opaque host revision or equivalent token whose invalidation covers provider/connection, model availability, enabled status and relevant variant changes. At commit the host must atomically compare that token together with the other [commit guards](README.md#shared-contracts), or demonstrably serialize all corresponding changes. A model name, metadata catalog, auth presence, past success, price, timestamp, or user preference alone is not proof. Even a verified host selection signal is not a guarantee that a provider request will succeed: remote outages, quota and later revocations remain ordinary host errors and never authorize a hidden retry.

The spike must identify the actual API, host documentation or pinned source contract, token invalidation rules, and reproducible tests for disabling/removing a candidate, changing connection and variant, and changing state between validation and commit. Record exactly which guarantees are documented versus inferred and the observed requests. If any required signal, invalidation or atomicity cannot be established, eligibility or freshness is `unknown` and the host is a no-go for automatic routing. A simulated provider validates integration behavior, not live account entitlement; the release evaluation must separately exercise the chosen real connection without publishing credentials.

Variants are scoped to one model and connection. A label alone does not establish reasoning semantics; use host-documented semantics or an explicit user mapping. A default variant may be selected only when the host proves it is valid and no explicit effort is being overridden. Never carry a variant between models merely because the IDs match.

## Lifecycle and failure

Refresh by a verified host lifecycle. Connection, configuration, availability, or revision changes invalidate the snapshot. Check the target against the same current connection and revision immediately before committing a decision; validation and commit must be atomic or reject stale revisions. A timestamp-only cache or a prior successful request cannot prove current access. The host adapter and catalog share the 200 ms decision deadline; timeout, stale data, unavailable access, malformed fields, or unsupported freshness guarantees produce `keep` and a bounded reason. The host owns any original-request error.

Model-role preferences reference discovered identities, not definitions. A newly discovered model is visible without a plugin release but is not assigned a role unless explicitly configured or a documented, validated host signal supports it. Invalid or retired role entries are reported, not silently substituted. The normalized snapshot retains the provider/model identifiers and internal connection identity required for isolation; it excludes credentials, authentication tokens, provider request bodies and other secret material.

## Acceptance

Fixtures cover new, removed, disabled and retired models; complete versus incomplete snapshots; account/connection swaps; stale revisions; unknown limits and capabilities; malformed metadata; a custom variant with unknown semantics; and a variant valid on one model but not another. The real host test must identify proof provenance and demonstrate invalidation and atomic guard rejection, not merely pass a fake revision fixture. Every selected candidate must satisfy verified eligibility at commit time. A proven pre-commit timeout or unavailable snapshot performs no router mutation and preserves the latest authoritative host selection, including intervening user changes; an ambiguous commit is handled as `indeterminate`, not as a proven keep.
